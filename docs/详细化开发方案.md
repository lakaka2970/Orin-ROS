### 1.2 上电顺序

**Radar 和 Camera 先上电 → 再启动 Orin 计算平台。**

### 1.3 全局时间戳要求

> **所有 Rx 节点必须在数据采集第一时间注入全局统一时间戳，精度为微秒（μs）。**

时间戳贯穿整个数据链路，从采集→处理→可视化→日志，全程透传不丢失。所有输出文件以时间戳（μs）命名。

## 三、各节点详细开发需求

### 3.1 Node: ADC Rx（雷达ADC数据接收节点）

#### 基本规格

| 参数 | 值 |
|------|-----|
| 帧率 | **15 Hz** |
| 每组数据量 | **16 MiB** (8T8R ctrx0 半集) |
| 数据结构 | 每 chirp **2048 个 int16 采样点**，共 **512 chirps × 2 groups × 4 RX**|
| 时间戳 | 全局统一，微秒精度 |

#### 数据维度解读

```
ADC数据形状: [1024 chirps × 4 RX × 2048 samples] × int16(2 bytes)
           = 512 chirps/group × 2 groups × 4 RX × 2048 × 2 bytes
           = 16,777,216 bytes ≈ 16 MiB
```

#### 开发任务

- [ ] **消息定义**：定义 ADC 原始数据消息类型，包含：
  ```
  std_msgs/Header header          # 含全局时间戳(μs)
  uint32 num_chirps               # 1024 (512 chirps × 2 groups)
  uint32 num_rx_antennas          # 4
  uint32 num_samples_per_chirp    # 2048
  int16[] data                    # 1024×4×2048 = 8,388,608 个采样点
  ```
- [ ] **零拷贝通信**：16 MiB/帧 × 15 Hz = **240 MiB/s** 吞吐（8T8R ctrx0 半集），使用 ROS2 Intra-process 或共享内存避免序列化开销
- [ ] **采集频率控制**：实现 15Hz 定时器或硬件触发采集
- [ ] **时间戳注入**：在 v4l2 读取数据的第一时间打戳，使用 `CLOCK_MONOTONIC` 或硬件 PTP 时钟
- [ ] **缓冲区管理**：设计环形缓冲区，建议大小 ≥ 3 帧（96MB），防止处理延迟导致丢帧
- [ ] **参数化配置**：帧率、数据维度等通过 YAML 参数文件配置，支持运行时调整

### 3.4 Node: R SP MIL Python & R SP Cuda（雷达信号处理节点）

#### 启动模式需求（重要变更）

> **可以启动二者其中任意一个，或同时启动二者。需要便于使用各种启动模式（快捷命令行或便捷参数修改），各种启动模式下都不影响整体框架运行。**

#### 四种启动模式

| 模式 | 命令/参数 | 说明 |
|------|----------|------|
| **仅 Python** | `ros2 launch ft_radar rsp_mode:=python` | 开发调试，算法验证 |
| **仅 CUDA** | `ros2 launch ft_radar rsp_mode:=cuda` | 生产部署，GPU加速 |
| **双路并行** | `ros2 launch ft_radar rsp_mode:=both` | 对比验证，结果一致性检查 |
| **双路对比** | `ros2 launch ft_radar rsp_mode:=both_compare` | 并行运行 + 自动对比输出差异 |

#### 开发任务

- [ ] **Launch 文件设计**：
  ```python
  # ft_radar_launch.py
  rsp_mode = LaunchConfiguration('rsp_mode', default='cuda')
  
  # 条件启动逻辑
  python_enabled = PythonExpression(["'", rsp_mode, "' in ['python', 'both', 'both_compare'"])
  cuda_enabled = PythonExpression(["'", rsp_mode, "' in ['cuda', 'both', 'both_compare'"])
  ```
- [ ] **话题命名隔离**：双路运行时输出不同话题，避免冲突：
  ```
  /processing/radar/det_list_python    # Python路径输出
  /processing/radar/det_list_cuda      # CUDA路径输出
  /processing/radar/det_list           # 主输出（根据模式选择）
  ```
- [ ] **下游节点适配**：Rviz_radar、Logging、3D Object Detection 节点需能根据配置选择订阅哪个 det_list 话题，或同时订阅两个
- [ ] **速度模糊消除算法**：
  - 输入：ADC 数据 + vdd（车辆速度用于补偿）
  - 核心：FFT 多普勒处理 + 速度模糊消除（利用 `ambgt` 速度模糊窗宽信息）
  - 输出：Det List（雷达目标列表）
- [ ] **CUDA 版本优化**：使用 cuFFT、CUDA Graphs、统一内存等 Jetson 优化技术
- [ ] **一致性验证工具**（both_compare 模式）：自动对比两路输出的 Det List 差异，生成差异报告

### 3.9 Node: Logging（数据日志记录节点）— 重大变更

| 来源 | 数据 | 备注 |
|------|------|------|

#### 5个独立开关控制

> **Logging开关作用是控制任意通道的数据进行录制。**

```yaml
logging:
  switches:
    enable_adc: true          # 开关1: ADC原始数据
    enable_image: true        # 开关2: 相机图像
    enable_det_list: true     # 开关3: 雷达检测列表
    enable_ego_motion: true   # 开关4: 自车运动数据
    enable_obj_list: true     # 开关5: 3D目标列表
```

- [ ] 每个开关独立控制对应通道的录制启停
- [ ] 支持运行时动态切换（`ros2 param set`）
- [ ] 开关状态记录到日志元数据中

#### 帧数限制

| 数据类型 | 最大帧数 | 存储估算 |
|----------|---------|---------|
| ADC | **100 帧** | 100 × 16 MiB = **1.6 GB** |
| image | **1000 帧** | 1000 × 16KB ≈ **16 MB**（若为JPEG则更大） |
| Det_List | **1000 帧** | 取决于每帧目标数 |
| ego_motion | **1000 帧** | 1000 × ~100B ≈ **100 KB** |
| obj_list | **1000 帧** | 取决于每帧目标数 |

- [ ] 达到上限后的策略需确认（停止记录 vs 循环覆盖），建议默认**停止记录并通知**
- [ ] 实时显示各通道已录制帧数/上限

#### 输出文件（与 FT_radar_dataset_requirement.md 对齐）

| 输出文件 | 格式 | 说明 | 命名规则 |
|----------|------|------|----------|

#### det_list.pcd 格式

- [ ] 标准 PCL PCD 格式 (v0.7)，支持 ASCII 和 Binary 两种 DATA 模式。

pycd4 是一个用于处理 PCD（Point Cloud Daa）文件的现代 Python 库，使用 Python 3 编写，其核心是 PointCloud 类，所有 PCD 文件都会读取为这个对象。

PCD是点云库（PCL，Point Cloud Library）的原生文件格式，而v0.7是官方指定的标准版本。

## 四、数据格式与消息定义（融合 FT_radar_dataset_requirement.md）

### 4.1 坐标系定义

```
        X (前方)
        ↑
        |
        |
Y ←─────● (后轴中心接地点)
        |
        |
        Z: 垂直向上 (右手坐标系)
```

| 轴 | 方向 | 正值含义 |
|----|------|---------|
| X | 车辆正前方 | 前方 |
| Y | 车辆左侧 | 左侧 |
| Z | 垂直向上 | 上方 |
| 原点 | 后轴中心接地点 | - |

**Local 坐标系**：车辆上电时的后轴中心位置，轴方向与上电时刻车辆坐标系一致。

### 4.2 雷达点云数据字段（det_list → PCD/CSV）

Logging 输出的 `det_list.csv` 和 `det_list.pod` 字段定义：

| # | 字段名 | 类型 | 单位 | 必需性 | 描述 |
|---|--------|------|------|:------:|------|
| 1 | `x` | float32 | m | **必需** | 车辆系纵向坐标（前方为正） |
| 2 | `y` | float32 | m | **必需** | 车辆系横向坐标（左侧为正） |
| 3 | `z` | float32 | m | **必需** | 车辆系垂直坐标（上方为正） |
| 4 | `range` | float32 | m | **必需** | 径向距离（雷达传感器坐标系） |
| 5 | `azimuth` | float32 | rad | **必需** | 方位角（雷达传感器坐标系） |
| 6 | `elevation` | float32 | rad | **必需** | 俯仰角（雷达传感器坐标系） |
| 7 | `RCS` | float32 | dBsm | **必需** | 雷达散射截面积，值域 [-100, 129.37] |
| 8 | `SNR` | float32 | dB | 可选 | 信噪比，值域 [0, 63.75] |
| 9 | `ambgt` | float32 | m/s | **必需** | 速度模糊窗宽（FFT多普勒最大不模糊度范围） |
| 10 | `exist_prob` | uint8 | [0,255] | **必需** | 存在概率，≥30保留，255=无效 |
| 11 | `multi_tgt_prob` | uint8 | [0,255] | 可选 | 多目标概率，255=无效 |
| 12 | `ambgt_prob` | uint8 | [0,255] | **必需** | 模糊概率，≥40保留，255=无效 |
| 13 | `raw_doppler` | float32 | m/s | **必需** | 原始多普勒径向速度（经硬件一次解模糊） |
| 14 | `idx` | uint8 | - | **必需** | 多普勒解模糊索引；255=SNA(无效)；0=解模糊失败 |

**关键过滤规则**：

| 过滤器 | 条件 | 默认阈值 |
|--------|------|----------|
| ROI | x/y/z 超出包围盒 | x∈[-80,200], y∈[-40,40], z∈[-15,15] m |
| 高度 | \|z\| >= \|x\| × 0.1 + 2 | 自适应 |
| RCS | 10m内: RCS≤-40; 10m外: RCS≤-20 | dBsm |
| 存在概率 | exist_prob < 30 | - |
| idx | idx == 255 (SNA) | - |
| 模糊概率 | ambgt_prob < 40 | - |

### 4.3 3D目标数据字段（obj_list）

| # | 字段名 | 类型 | 单位 | 描述 |
|---|--------|------|------|------|
| 1 | `object_id` | uint64 | - | 目标跟踪ID |
| 2 | `tracked_times` | uint64 | - | 跟踪帧数 |
| 3 | `score` | float32 | [0,1] | 置信度/障碍物概率 |
| 4 | `x` | float32 | m | 车辆系bbox中心X |
| 5 | `y` | float32 | m | 车辆系bbox中心Y |

## 五、时间同步机制

### 5.1 全局时间戳方案

| 项目 | 规格 |
|------|------|
| 时钟源 | `CLOCK_MONOTONIC`（开发阶段）/ PTP硬件时钟（生产阶段） |
| 精度 | 微秒（μs） |
| 注入位置 | 所有 Rx 节点数据采集第一时间 |
| 透传规则 | 后续节点不得覆盖，仅在消息头 `header.stamp` 中传递 |

### 5.2 多传感器时间对齐策略

- **主时钟基准**：以 ADC Rx 的 15Hz 帧时钟为主基准
- **Camera Rx（30Hz）**：每帧独立时间戳，Logging 时按最近邻匹配到雷达帧
- **Vehicle Data Rx（50Hz）**：高频数据，Logging 时按时间戳插值或最近邻匹配
- **ego_motion.csv**：单文件按时间戳排序存储，程序处理时按时间戳交替处理
