## 一、项目概述

### 1.1 项目目标

构建基于 **NVIDIA Jetson AGX Orin** 的毫米波雷达多传感器融合感知框架，实现：
- FVR60 4D成像雷达（Infineon CTRX8188F）数据采集与处理
- 相机（Rmoncam A2 1080P）图像采集
- 车辆动态数据（CAN总线）接入
- 实时雷达信号处理（RSP）与目标检测
- 符合 FT Radar Dataset Requirement 标准的数据集生成

### 1.2 技术栈

| 组件 | 技术选型 |
|------|---------|
| 硬件平台 | NVIDIA Jetson AGX Orin 64GB |
| 操作系统 | Ubuntu 20.04 / 22.04 |
| 中间件 | ROS2 Foxy / Humble |
| 编程语言 | C++ (数据采集层) + Python (算法层) |
| GPU加速 | CUDA, cuFFT, PyTorch |
| 通信机制 | FastDDS 共享内存传输 |

### Phase 9: 硬件级时间戳与 Camera 重写 (2026-07-16)

#### 2026-07-16 - 硬件级时间戳重构
- **开发者**: zhengyuan.liu
- **核心工作**:

**1. 时间戳机制从 ROS Time 改为内核硬件时间戳**:

| 传感器 | 时间戳来源 | 说明 |
|--------|-----------|------|
| ADC | V4L2 `v4l2_buffer.timestamp` | 内核驱动在帧接收完成时设置 |
| Camera | V4L2 `v4l2_buffer.timestamp` | 同上 |
| Ego-motion | SocketCAN `SIOCGSTAMP` ioctl | 内核在 CAN 帧到达时设置 |

- 三者同源 (`CLOCK_MONOTONIC`)，无时钟偏移，可直接对齐
- Launch 文件显式设置 `use_sim_time: false`，确保时钟一致性
- 时间戳精度: 微秒级 (10⁻⁶ s)

**2. Camera 节点完全重写**:
- 从 OpenCV `VideoCapture` 改为 Raw V4L2 mmap streaming
- 新增 `V4L2Camera` 结构体，封装 V4L2 设备生命周期
- 使用 `V4L2_PIX_FMT_MJPEG` 格式，MJPEG 帧直接写入 `.jpg` 文件
- **消除 decode+encode 开销**: 原来 OpenCV 做 MJPEG→BGR→JPEG，现在直接写盘
- 移除 OpenCV 依赖 (`CMakeLists.txt`)
- 添加 `VIDIOC_S_PARM` 硬件帧率控制，与软件帧率统一

**3. SocketCAN 完整实现**:
- 5 报文解析 (车速/档位/横摆角/加速度/转向角)
- Motorola (MSB) 字节序信号提取
- 超时回退默认值机制
- CSV 回退模式保留
- `SIOCGSTAMP` 硬件时间戳

**4. V4L2 Buffer 监控工具**:
- 新增 `v4l2_buffer_monitor.sh` 脚本
- 使用 `strace` 监控 V4L2 ioctl (VIDIOC_QBUF/DQBUF)

## 四、核心技术突破

### 4.1 大消息传输优化

**问题**: 32MB/帧 ADC 数据通过 DDS 传输导致严重丢包 (480MB/s 带宽需求)

**解决方案**: 文件路径发布模式
```
原始模式: ADC Rx → DDS (32MB/帧) → RSP (大量丢包)
优化模式: ADC Rx → 同步写入文件 → DDS (文件路径, ~20KB) → RSP (读取文件)
```

**效果**: DDS 带宽降低 99.99%，零丢包

### 4.2 V4L2 Buffer 排空效应

**问题**: V4L2 设备启动时 buffer 预填充旧数据，导致前几帧时间戳不准确

**解决方案**: Warm-up 机制
1. 启动时不立即开始 V4L2 streaming
2. 等待 warmup_sec (默认 5s) 让设备稳定
3. 调用 `flush_buffers()` 清空预填充 buffer
4. 开始正常采集

### 4.3 多传感器时间同步

**方案**: 内核硬件时间戳 (Kernel-Level Timestamps)
- ADC/Camera: V4L2 `v4l2_buffer.timestamp` (内核驱动在帧接收完成时设置)
- Ego-motion: SocketCAN `SIOCGSTAMP` ioctl (内核在 CAN 帧到达时设置)
- 三者同源 (`CLOCK_MONOTONIC`)，无时钟偏移，可直接对齐
- 微秒精度 (有效精度 10⁻⁶ s)
- `use_sim_time: false` 确保时钟一致性
- 下游节点透传，禁止覆盖
- 文件命名使用时间戳 (μs)

**时间戳单位流转**:
```
硬件层: struct timeval { tv_sec(秒), tv_usec(微秒) }
  ↓
ROS 消息: header.stamp { sec(秒), nanosec(纳秒) }  ← tv_usec × 1000
  ↓
文件名/CSV: int64 微秒整数  ← sec × 10⁶ + nanosec / 10⁶
```

### 4.4 双 CTRX 数据合并

**硬件架构**: 
- CTRX0: 8T8R, 4 RX, 16MB/帧
- CTRX1: 8T8R, 4 RX, 16MB/帧
- 合并后: 16T16R, 8 RX, 32MB/帧

**实现**: 
- V4L2 mmap 同时采集两个设备
- 逐帧拼接为完整 32MB 数据
- 数据结构: 1024 chirps × 8 RX × 2048 samples

### 4.5 GPU 加速 RSP

**CUDA 优化**:
- cuFFT: 快速傅里叶变换
- 批量 DOA: 并行角度估计
- 峰值检测: GPU 加速 CFAR

**性能**: 从 ~80ms/帧 (CPU) 降至 <20ms/帧 (GPU)

## 六、关键决策记录

### 6.1 DDS 选型: FastDDS vs CycloneDDS

**决策**: 使用 FastDDS (ROS2 Foxy 默认)

**原因**:
- FastDDS 2.1.4 内置共享内存传输
- CycloneDDS 0.7.0 (Foxy 版本) 不支持 SHM (0.9.0+ 才有)
- 32MB 大消息必须走 SHM，UDP 分片导致严重丢包

**教训**: 先确认 RMW 版本和能力，SHM 支持是分水岭

### 6.2 数据采集层语言选择

**决策**: C++ 实现数据采集层，Python 实现算法层

**原因**:
- C++: 高性能，适合 32MB/帧 × 15Hz 的数据采集
- Python: 快速迭代，适合算法开发和调试
- 混合架构: 性能与开发效率平衡

### 6.3 文件路径发布模式

**决策**: rx 节点写入文件后发布路径，而非直接传输原始数据

**原因**:
- DDS 带宽限制 (480MB/s 不可持续)
- 文件路径消息仅 ~20KB，降低 99.99% 带宽
- 磁盘 I/O 比网络传输更可靠
- 便于离线分析和数据回放

### 6.4 Warm-up 机制

**决策**: 实现 V4L2 buffer 排空机制

**原因**:
- V4L2 设备启动时 buffer 预填充旧数据
- 直接采集会导致前几帧时间戳不准确
- Warm-up + flush 确保数据质量

## 十、经验总结

### 10.1 技术经验

1. **大消息传输必须走 SHM**
   - UDP 分片不可靠 (32MB → 23000 分片)
   - 同机通信优先使用共享内存

2. **Python ROS2 回调串行执行**
   - GIL 限制，重操作必须卸到独立线程
   - 异步写入架构是必须的

3. **QoS 匹配是硬约束**
   - Publisher/Subscriber reliability 必须一致
   - Best Effort 在同机 SHM 下等价于 Reliable

4. **字段类型要匹配实际数据范围**
   - Unix 微秒时间戳需 uint64
   - uint32 仅能容纳 ~71 分钟

5. **异常处理要考虑级联效应**
   - 一个函数崩溃不能阻断整个 pipeline
   - 关键路径用 try/except 包裹

### 10.2 开发经验

1. **先确认 RMW 版本和能力**
   - 不同版本的 DDS 支持的特性差异巨大
   - 文档可能过时，以实际测试为准

2. **XML 配置要验证版本兼容性**
   - 非法元素导致静默回退
   - 使用最小化配置开始

3. **混合语言架构的优势**
   - C++ 负责性能关键路径
   - Python 负责快速迭代
   - 通过 ROS2 话题解耦

4. **文档与代码同步更新**
   - 每次重大变更同步更新文档
   - 代码注释解释"为什么"，文档解释"是什么"

### 10.3 项目管理经验

1. **分支策略**
   - feature 分支开发，master 分支稳定
   - 定期合并，避免长期分叉

2. **代码审查**
   - 使用 AI reviewer 辅助审查
   - 关键模块多人 review

3. **测试驱动**
